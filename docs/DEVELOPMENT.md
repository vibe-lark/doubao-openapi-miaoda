# 开发与验证

## 保持原版界面

原版源码位于 `client/src/pages/doubao/original/doubao-work-main.html`。其 SHA-256 记录在根目录 SOURCE.json。

业务变更优先发生在 `platform.ts`、前后端合同和服务端模块。`originalPage.ts` 的替换边界应明确；如果原版源码升级，先检查替换是否命中，再在同一浏览器与偏好下核对首页、会话详情、已授权/未授权、多个窗口尺寸和侧栏交互。不要把 UI 重写当作平台适配。

原版 HTML 中保留了来源快照的演示应用常量。实际 OAuth、上游调用和凭据存储均读取自己后端的 DOUBAO_* 配置；授权地址会被 `originalPage.ts` 替换，不会使用来源快照的妙笔授权入口。该常量仍用于前端退出状态键等原版页面逻辑，不能据此复用任何应用凭据。

## 本地检查

```bash
bun install --frozen-lockfile --ignore-scripts
bun run type:check
bun test tests
bun run eslint
bun run build:prod
```

GitHub CI 只安装依赖并执行这些不需要真实凭据的检查，不发起 OAuth、不调用真实豆包接口、不发布应用。应用实际运行必须在自己的妙搭环境配置平台身份和服务端环境。

## 验证记录如何阅读

[002-original-ui-validation.json](002-original-ui-validation.json) 记录来源应用的六组界面对比，以及模拟接口的消息接收、中断、退出验证。这些是固定输入下的验证，不能据此宣称真实用户授权或真实模型输出已验收。

README 的两张截图取自这组固定测试数据。模板可能显示平台自身标识；对比应用 UI 时，使用平台内置个人偏好关闭标识，而非修改 SDK 隐藏它。

单元测试覆盖：

- AES-GCM 加密与应用/用户绑定，错误密钥或其他用户不可解密。
- 助手 reply_id 与内容排序。
- 空终态消息及缺失会话 ID 的异常处理。
- 思考摘要、工具名称和链接保留。
- OAuth 头像资料保留在加密凭据中。

自己的应用还需要验证真实权限、回调、refresh token 轮换、授权撤销、并发请求与完整生成链路。

## 故障定位

| 现象 | 优先检查 |
| --- | --- |
| 未配置授权 | dev/online 五个 DOUBAO_* 变量是否正确 |
| OAuth 回调 URL 错误 | 飞书登记地址与当前应用线上回调是否完全匹配 |
| 平台拒绝访问或缺少身份 | 是否通过自己的妙搭应用入口、用户是否有可见权限 |
| 豆包返回未授权 | scope、接口资格、用户授权及过期/撤销情况 |
| 消息重复 | 是否把完整快照当 delta 追加，或自动重试了写请求 |
| 授权窗口被拦截 | 是否仍在点击事件中同步调用 window.open |
| 解密失败 | TOKEN_KEY 是否变化，凭据是否属于当前应用与用户 |

日志只保留状态码、业务错误码和安全的关联标识，不记录令牌、授权码、Cookie、应用密钥或完整消息正文。
